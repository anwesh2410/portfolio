How I keep an LLM sales agent from saying things that aren't true

Anwesh Ale · AI engineer

At Wisemate I build the AI agents that write and send outbound sales emails for B2B customers. An email that has gone out can't be taken back, so the expensive failure isn't a bad sentence. It's a confident, specific claim that isn't true. We had exactly that once: the model invented pricing, and it reached a real email. This is the pipeline I built so that it can't happen again.

1. Only grounded facts get into the prompt

The model writes from a short company brief, not the raw website. When the brief is extracted, the model must return each fact with the quote it came from. A fact is kept only if that quote is a verified, exact substring of the customer's knowledge base. Anything the model "remembers" or paraphrases into existence is dropped before generation starts.

2. A judge, then an editor

Generation is staged: 1. Judge. An LLM judge checks the prospect and the draft against the brief and returns a structured, schema-validated decision. 2. Editor. An LLM editor rewrites only what the judge flagged.

Each stage has one narrow job, which makes failures easy to attribute and test.

3. One fail-closed gate before anything sends

Every outbound path, on every channel, passes through a single pre-send gate: - If any check fails, or the checker itself errors, the message is blocked, not sent. "Fail closed" means an outage of the checker can't turn into unchecked emails. - Every decision is written to an audit trail of pipeline events, so a blocked message can be traced back to the exact claim and stage.

4. The send itself is boring on purpose

The quality gate is useless if retries can send twice. Sends are idempotent: - Each send has an idempotency key. - Workers claim jobs with Postgres FOR UPDATE SKIP LOCKED. - An orphan reaper recovers jobs whose worker died mid-claim. - Bounces and unsubscribes cancel the rest of a sequence.

If the LLM's decision is invalid, the system falls back to a safe template rather than guessing.

What I'd tell another team

  • Put the guard at the chokepoint. One gate that every channel passes through beats a check in each sender.
  • Make the model show its source. Then verify the source mechanically, without asking another model.
  • Treat "the checker failed" as "no".
  • Log the reason for every block. Debugging an agent is mostly reading why it refused.
